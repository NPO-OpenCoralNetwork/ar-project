## 地図・3Dデータの使用条件

### 企画への示唆
- 富山市と立山町には PLATEAU がないので、最初の地域の「絵地図フィールド」は OSM（建物の形・道路・川・寺社のPOI）と地理院の標高タイル（PNG形式。DEM5A/DEM10B を想定）から作る必要があります。手順は、事前に処理して高さを段数に丸め、瓦屋根や塀を手続き的に生成し、glTF に焼く形です。PLATEAU は、建物 LOD2 とアーケード LOD3 がある高岡市で、パイプラインの検証や2つ目の地域に使えます。
- 地形には、区分(2)の「標高タイル（基盤地図情報数値標高モデル）」を使います。事前に加工してゲームに同梱しても、出典と加工の旨を書けば済むと読めます。一方、標準地図や淡色地図（基本測量成果）をテクスチャとして焼き込むのは避けます。リアルタイム表示以外で使うと申請が必要になる場合があるためです。最適化ベクトルタイルは試験公開なので、製品版が依存するデータ源にはしません。
- OSM から和風の箱庭を作る変換（選別・簡略化・PLATEAU との統合など）は、Derivative Database を作ることになると考えておくのが安全です。対策は3つです。(1) ODbL 4.6(b) を満たすため、変換スクリプトや手順を無償で公開する。(2) クライアントに配る中間ベクタデータ（GeoJSON など）は ODbL で提供する前提にする。(3) 妖怪の配置・物語・お守り・御朱印などの独自データは別ファイルに分け、Collective Database として扱って ODbL が及ばないようにする。
- 01-tech-stack-decision.md の「MapLibre＋OSM系タイル」は、製品版では tile.openstreetmap.org を使えません。オフライン利用・先読み・一括取得が禁止で、商用は打ち切りがありうるためです。OSM の抽出データから自前でベクタタイルを作って配信する前提に直すのがよいです。
- Google Photorealistic 3D Tiles は、絵地図フィールドの土台には向きません。和風に作り直すためのメッシュ抽出、キャッシュ、オフライン利用ができず、Google 以外の地図との併用も制限され、1,000ルート要求ごとに $6 程度かかるためです。使うとしても「本物の景色を見る」写実モードに限り、そのモードでは OSM や地理院の地図を同じ画面に出さないようにします。MVP では使わないことを勧めます。シェーダーで見た目だけを和風にすることの可否は未確認なので、使う場合は Google に確認してからにします。
- 初三郎の1932年版と1936年版の富山鳥瞰図には、立山の名所（雄山神社・地獄谷・弥陀ヶ原・室堂・称名滝・立山温泉・剱岳・浄土山）が名札付きで描かれていて、保護期間も切れていると判断できます。次の用途に使えます。(1)「遊べる地域を選ぶ」画面の地域カード、ロード画面、図鑑の背景。(2) フィールドの見た目（U字に曲げた構図や誇張の表現）の手本。(3) 名所ラベルの置き方の参考。使う前に日文研へ利用概要を連絡し、画像ごとに「国際日本文化研究センター所蔵」と表記します。切り抜きや色調変更などの改変は、事前に可否を問い合わせます。
- 昭和11年（1936年）頃の富山の資料が複数あります（富山市、東岩瀬、日満産業大博覧会。博覧会の図は作者不明）。これを使って、現代の町と「初三郎が描いた昭和初期の富山」を切り替える時代レイヤーを作り、現地でしか手に入らない御朱印風の収集物と組み合わせる案が考えられます。
- クレジット画面を最初から設計に入れておきます。起動時のスプラッシュに加えて、設定の「データライセンス」に次を載せます。「© OpenStreetMap contributors（ODbL、/copyright へのリンク）」「地理院タイル（標高タイル）を加工して作成（一覧ページへのリンク）」「国土交通省 PLATEAU（○○市）を加工して作成」「国際日本文化研究センター所蔵（初三郎の図）」。地域ごとに使うデータ源が変わるので、表示中の地域に合わせてクレジットを切り替える仕組みにしておくと拡張しやすくなります。
- 世界中で遊べる地域を選ぶ構想では、PLATEAU と地理院は日本でしか使えません。海外でも共通に使えるのは OSM と全球の DEM ですが、地理院の地球地図全球版標高は z0〜8 で粗すぎます。海外の DEM（Copernicus など）のライセンスと解像度は今回調べていません。次の調査テーマです。

### 調べたこと
#### 1-a) PLATEAU（3D都市モデル）の整備都市に富山市・立山町は含まれるか（確度: 確認済）

含まれていません（2026-10-16 時点の公開データ）。PLATEAU のオープンデータ一覧に載っている富山県の自治体は、高岡市（2024年度）、射水市（2024年度）、舟橋村（2025年度）の3つだけです。G空間情報センターの CKAN API で、都市局（organization:toshi）の全526データセットを県コード16で絞り込んでも、出てきたのは plateau-16202-takaoka-shi-2024、plateau-16211-imizu-shi-2024、plateau-16321-funahashi-mura-2025 の3件でした。富山市（16201）と立山町（16322）はありません。参考までに高岡市（V4、最終更新 2026-04-07）の内容は、建物 LOD0〜2（CityGML/3D Tiles）、道路・鉄道・土地利用 LOD1（CityGML/MVT）、アーケード LOD3、地形 LOD1 などです。2026年度以降に富山市・立山町が整備される予定があるかは、一次情報を確認できず不明です。

#### 1-b) PLATEAU のライセンス（商用ゲームで使えるか、表示義務）（確度: 確認済）

商用ゲームでも使えます。PLATEAU サイトポリシーの「3. コンテンツの利用」によると、G空間情報センターで公開している3D都市モデルのオープンデータは、著作権が各地方公共団体にあり、『公共データ利用規約（第1.0版）』（PDL1.0）に準拠した条件で使えます。PDL1.0 の本文には「商用利用も可能です」、複製・公衆送信・翻案等を「自由に利用できます」と書かれています。義務は次の2つです。(1) 出典の記載（例:「出典：国土交通省 PLATEAUウェブサイト（当該ページのURL）」）。(2) 編集・加工した場合は、出典とは別に加工したことを記載すること（例:「…を加工して作成」「…をもとに○○株式会社作成」）。加工した情報を国交省が作ったかのように見せることは禁止です。また、本ルールは CC BY 4.0 と互換で、利用者は CC BY に従って使うこともでき、ODC-BY や ODbL での利用も妨げないと明記されています。注意点として、測量法に基づく公共測量成果など、個別の法令で利用が制約されるコンテンツがありうるとされています。なお、データセットのライセンス欄には「PLATEAU Site Policy『３．著作権について』に拠る」とありますが、現行のサイトポリシーでは該当する節の見出しが「3. コンテンツの利用」になっています。

#### 2) 国土地理院のベクトルタイル・標高タイル（DEM）を商用ゲームで使う条件（確度: 一部確認）

【共通】国土地理院コンテンツ利用規約は「特段の記載が無い限り公共データ利用規約（第1.0版）（PDL1.0）」を適用しています。PDL1.0 は商用利用・翻案が可能で、条件は出典の記載と、加工した場合の加工の旨・主体の記載です。今回見たページに「政府標準利用規約」という名称は出てきませんでした。PDL1.0 は政府標準利用規約の後継と理解していますが、その点は今回一次情報で確認していません。ゲーム利用を直接扱った記述は、国土地理院の Q&A にもタイル一覧にもありません。
【地理院タイル一覧の区分】(1) 基本測量成果：標準地図・淡色地図など（名称は「電子地形図（タイル）」）。測量法に基づく申請が必要な場合があります。(2) 基本測量成果以外で、出典の記載だけで使えるもの。(3) それ以外。どの区分でも、ウェブサイトやアプリが地理院サーバーからリアルタイムに読み込んで表示する場合は、申請不要で出典の明示だけで足ります。出典は「国土地理院」や「地理院タイル」などと書き、タイル一覧ページへリンクします。
【標高タイル】「標高タイル（基盤地図情報数値標高モデル）」は区分(2)なので、出典の記載で申請なしに使えます。DEM1A は z1〜17、DEM5A/5B/5C は z1〜15、DEM10B は z1〜14 です。テキスト形式は令和6年10月から更新が止まっていて、PNG 形式を使います。加工した場合の記載例として、規約自体が「地理院タイル（標高タイル（基盤地図情報数値標高モデル））を加工して作成」を挙げています。
【ベクトルタイル】「最適化ベクトルタイル」（PMTiles 版あり）は国土地理院コンテンツ利用規約に従って使えます。出典は「国土地理院最適化ベクトルタイル」などと書きます。ただし「試験公開」で、公開期間は「公開終了まで」とされています。位置づけは「基本測量成果と位置付けているものではありませんが、基本測量成果としての提供を検討するにあたって、試験的に公開」とあり、データソースは数値地図（国土基本情報）です。
【不明な点】タイルをダウンロードして加工し、ゲームのアセットとして同梱・配布する場合に測量法上の申請が要るかどうかは、標準地図・淡色地図のラスタでは「必要な場合がある」とされていますが、ベクトルタイルについての明記は見つかりませんでした。「地理院地図」「地理院タイル」は国土地理院の登録商標です。

#### 3) OpenStreetMap（ODbL）のデータをゲームの地形・建物生成に使う場合の義務（Produced Work と Derivative Database の違い、ゲーム内データとして配布する場合）（確度: 一部確認）

【基本】OSM のデータは ODbL で提供され、OpenStreetMap とその貢献者をクレジットすれば、コピー・配布・改変ができます。改変したり、それを土台にした結果を配布する場合は、同じライセンスでしか配布できません。
【Produced Work（PW）】ODbL の定義では、データベースの全体または実質的部分を使って作った「作品（画像、映像、文章、音声など）」です。PW を公に使う場合は、ODbL 4.3 の通知（表示）だけが必要で、5.5(b) により PW を作っても Derivative Database（DD）にはなりません。OSMF の公式ガイドライン（2014年承認）は、成果物が「元データの抽出を目的とする」ならデータベース、そうでなければ PW、と区別しています。PNG・JPG・PDF・SVG などのラスタ画像や印刷地図は通常 PW で、Planet ダンプのようなデータベースダンプは PW ではないとしています。
【落とし穴】ODbL 4.4c・4.6 により、OSM を加工・選別・統合して作った DD から PW を作って公開すると、その DD も公に使ったことになります。そのため、DD 全体か、変更の差分か、変更の方法（アルゴリズム）を、ネット配布なら無償で提供しなければなりません。
【ゲームの場合】OSMF の帰属ガイドライン（2021-06-25 採択）に「Computer games and simulations」の節があります。表示場所は、起動時のスプラッシュ画面、ゲーム画面内、プレイ中、クレジット画面、メニューのどれでもよいとされています。最初の表示が簡略な場合は、詳細を適切な場所に置く必要があります。ODbL であることは、openstreetmap.org/copyright へのリンクで示せます。
【配布するゲーム内データ】3D メッシュや GeoJSON・ベクタタイルを PW と見るか DB と見るかについて、公式ガイドラインに具体例はありません（Examples は「None」）。参考になるのはコミュニティ Wiki で、これは正式見解ではないと明記されています。Legal FAQ は「OSM データを含むゲームは PW」としています。Garmin .img のようなベクタ形式は、視覚的な地図として配るなら PW、抽出して DB として使えば派生物、という議論があります。ゲームクライアントに建物の形状や道路などを、そのまま取り出せるベクタデータとして配る場合は、DB（ODbL での提供が必要）と判断されるおそれがあります。ここは未確定です。
【他のデータとの組み合わせ】独立したデータセットを並べるだけなら Collective Database で、他のデータに ODbL は及びません。OSM の道と他のデータの道をつなぐなど、合わせて加工すると DD になります（コミュニティ Wiki の Legal FAQ の説明で、正式見解ではありません）。
【タイル配信】tile.openstreetmap.org は、オフライン利用・一括取得・先読みが禁止です。商用サービスは「いつでもアクセスを打ち切られうる」とされています。

#### 4) Google Photorealistic 3D Tiles を three.js で使う場合の規約上の制約（独自スタイルへの加工、キャッシュ、表示義務、料金）（確度: 一部確認）

【位置づけ】Map Tiles API は Google Maps Platform の Core Services に含まれます。
【キャッシュ・オフライン】ポリシー上、契約で定める限定的な条件を除き、事前取得・索引化・保存・キャッシュはすべて禁止です。Cache-Control の max-age などには従う必要があります。用途は地図の可視化に限られ、画像解析、物体検出、ジオデータの抽出・再販、オフライン利用はできません。ToS 3.2.3(a) は、タイルの一括ダウンロードや、サービス外での保存・再ホストを禁止しています。
【独自スタイルへの加工】自分の 3D オブジェクトを重ねるのは構いませんが、そのオブジェクトを 3D Tiles から抽出・トレース・派生させてはいけません。ToS 3.2.3(c) も Google Maps のコンテンツから新しいコンテンツを作ることを禁じています（例: 45°画像から 3D 建物を作る、Elevation API から地形モデルを作る）。このため、メッシュを取り出して和風に作り直す使い方はできません。一方、描画時にシェーダーで見た目だけを変える（トゥーン調など）ことの可否は、明文の規定を見つけられず未確認です。ロゴは一切改変してはいけません。
【併用の制限】ToS 3.2.3(e) は、Core Services を同じアプリ内で Google 以外の地図「with or near」で使うことを禁じています。OSM や地理院の地図と同じ画面・同じアプリで並べる設計は抵触するおそれがあります。
【表示義務】Google Maps のロゴを表示し、レンダラ（three.js など）のロゴと重ねたり隠したりしてはいけません。さらに、表示中のタイルの glTF asset に入っている copyright 文字列を集め、描画ビュー内に表示する必要があります。自前のモデルと混ぜる場合は、どの部分が Google のデータかを UI で明示しなければなりません。アプリの利用規約には、Google Maps の機能・コンテンツを含むことと、Google Maps 追加利用規約・Google プライバシーポリシーに従うことを記載する必要があります（ToS 3.2.2(a)）。COPPA 上の「子ども向けサービス」で使うことは禁止されています（ToS 3.1(c)(vi)）。
【three.js】公式ドキュメントでは「OGC 3D Tiles 対応の任意のレンダラ」が使えるとされています。例として挙がっているのは CesiumJS、Cesium for Unreal/Unity、deck.gl で、three.js（3DTilesRendererJS）は名前が出ていません。帰属表示の実装は自分で行う必要があります。
【料金】Enterprise SKU「Map Tiles API: Photorealistic 3D Tiles」の価格です（米国ドル、1,000イベントあたり、月間）。無料枠は月1,000イベントです。〜10万件は $6.00、10万1〜50万件は $5.10、50万1〜100万件は $4.20、100万1〜500万件は $3.30、500万件超は $2.40。使用量ページによると、日次クォータに数えるのはルートタイルセット要求（既定は1日10,000件）で、レンダラからのタイル要求は無制限です。1回のルート要求で、最長3時間分のセッションになります。課金イベントがルート要求であることは使用量ページからの理解で、SKU の課金定義の文言そのものは確認していません。
【その他】価格ページとポリシーページの最終更新は 2026-10-15、ToS の最終更新は 2026-08-26 です。EEA 向けには別規約がありますが、日本の請求先には通常の規約が適用されます。

#### 5-a) 吉田初三郎が富山・立山を描いた鳥瞰図は実在するか、所蔵先はどこか（確度: 確認済）

実在します。国際日本文化研究センター（日文研）の「吉田初三郎式鳥瞰図データベース」に次の作品があり、所蔵は日文研です。

(2) ID 004868865「富山市」。富山市役所の発行、1936年3月、20×100cm で、画像の題箋は「富山縣観光交通鳥瞰圖」です。

## 現地限定の先例と、御朱印・お守りまわりの注意

### 企画への示唆
- 【名前と見た目】ゲーム内のアイテムを『御朱印』『お守り』と呼んだり、それに似せたりしない。04 §7 の『護符・御朱印に似せない』を続ける。神社本庁は御朱印を『参拝した証』、お守りを『神さまのご加護を戴くもの』としており、個々の神社も『購入した品物ではなく授与品』と明言して転売を戒めている（彌彦神社・大神神社）。ゲームで模造品を集めさせたり売り買いさせたりすると、この線に正面からぶつかる。代わりに、宗教色のない印文化（御城印・御船印・ダムカード）に倣った『旅印（仮）』と、妖怪側の創作の『預かり物』（根付・鈴・羽など。04 の創作ルールに従う）にする。
- 【実在の授与品】ゲームで本物の代わりを出すのではなく、本物の場所へ導く。例えば雄山山頂の熊鈴付きお札（神主のお祓いを受けた人だけ）は再現せず、終章などで『本物は山頂で』と案内するだけにとどめる。寺社と組むのは、寺社側が言い出して監修する場合だけにする。竹神社や真如寺のデジタル御朱印も、主体は寺社か地域の法人だった。雄山神社の考えは未確認なので、立山博物館などを通じて直接相談する。
- 【お金を取る線】現地限定の印や預かり物は、課金やガチャで売らない。授与品に似たものを売ると、宗教界の『授与品は商品ではない』という感覚とぶつかる。寺社と組んで売れば、喜捨金か物品販売かという税務の線にもかかわる。収益は、ドラクエウォークの『リアルおみやげプロジェクト』のような地元の菓子・工芸との組み合わせや、宗教色のない現物（ダムカード型の配布カード）でつくるほうが安全。
- 【希少性の作り方】数量・期間・先着で限定して、寺社の窓口に行列をつくらせない（浅草神社の2019年、ちいかわ×護国寺の2024年の転売と混雑）。現地限定のものはアカウントに結びつけて譲れないようにし、転売の意味をなくす。人に贈れるのは、ドラクエウォークの金／銀トロフィーのように『白描版』だけ、とすれば、名誉は現地に行った人に残り、贈り物の楽しさも残る。
- 【おうちモード＝バーチャル街歩きの線引き】『家から地図で街に入って歩き回る』案は採れる。ただし、ポケモンGOの教訓（2020年に家で遊べるようにした仕様が主流になり、2023年に値上げと回数制限で削って大きく反発され、2025年に1日10回へ戻した。2021年の80m問題も同じ流れ）から、境界は最初に決めて、後から削らない。具体案: 家から入る街は全部『白描（墨の線画）の街』として歩けて、妖怪とも話せる。現地に立つと同じ地点が『彩色』され、『えにし』の打ち明け話が起きる。04 §3.6 の白描→彩色の軸を、そのまま街の見た目にも使う。
- 【現地の価値は上乗せで】家の遊びを罰したり窮屈にしたりして現地へ行かせるのではなく、現地での上乗せで差をつける。2023年の公開書簡が求めたのも『対面レイドの報酬を増やすこと』だった。地方に住む人、障害のある人、子育て中の人など、行けない人にとって、おうちモードは主な遊び方になりうる。モンハンNowのペイントボールのように『現地で縁の糸を結び、続きは家で話す』形は、04 の『なじみ以上は家で話せる』とすでに合っている。世界中の地域を選んで入る構想は、各地域に白描の街を用意する作業量が大きいので、MVP は立山・富山だけにする。
- 【位置偽装への対策】Webファーストなので、ブラウザの位置はDevToolsで簡単に書き換えられる。そこでGPSは、白描→彩色や出会いのような『偽装されても誰も損しない』価値にだけ使う。『えにし』や旅印のような価値の高い現地報酬にだけ、現地の物理トークンを足す。第一候補は NTAG 424 DNA の SUN タグ。タップごとにカウンタと署名入りのURLを出し、サーバーで確かめる。URLを開くだけなので、Web NFC（iOSでは使えないとみられる）は要らない。静的なQRは撮影・共有で破られる（仙台の事例）。使うなら、QR＋GPSの半径＋窓口の画面に出す時刻で変わるコード、のように重ねる。
- 【タグの置き場所と運用】タグやQRは寺社の境内に勝手に置かない。了承を得た立山博物館、観光案内所、駅、アルペンルートの施設、山小屋などに置く。盗難や破損、電波の届かない場所での検証、設置と維持の費用を11月の下見の調査項目に入れる。現金に近い景品を現地チェックインに結びつけない。結びつけると不正の動機が一気に強まる。
- 【リアルの『現地限定』とペルソナ】将来の現物連携は、ダムカード・マンホールカード方式（無料・現地だけ・1人1枚・郵送しない・転売目的は断る）が手本になる。富山県内のダムや連携施設で『妖怪札カード』を配るのは、宗教上の問題がない現地限定品になる。印集めの層は大きく（御船印 約4万ユーザー・78万枚、マンホールカード累計1,050万枚、100名城の完全制覇8,192人）、ペルソナA（御朱印帳3冊目）と重なる。ただ、御城印と御朱印は別の帳面にする慣習があるので、ゲーム内の帳面（縁帳）は御朱印帳とはっきり別物に見せる。
- 【寺社を地点にするときの手続き】2016年に出雲大社や広島の平和記念公園が、位置情報ゲームを断ったり削除を求めたりした。そのため、了承の前は社寺名や由緒を出さず『この地点』と書く方針（04）を続け、地点を外してほしいという申し出の窓口を、公開前から用意しておく。
- 【未確認のまま残る点】神社本庁がゲームやデジタル御朱印について出した公式見解、雄山神社の姿勢、峰本社の今の授与品と開いている期間、GPS偽装がどれくらい起きているかの統計、ドラクエウォークのおみやげ交換の公式仕様。これらは確認できていない。企画書には『要確認』と書き、現地の関係者への相談事項に入れる。

## three.js で箱庭を作る技術

### 企画への示唆
- おうちモードの「町に入る」は、実在の地図をそのまま 3D にするより、「OSM と標高データで下地を半自動で作る → 1地区（数百m四方）を手で様式化する → glTF の『地域パック』として焼いて配る」方式が現実的。公開 Overpass にアプリから直接問い合わせるのは規約上不適切なので、地域パックは開発時にスクリプトで作り、静的ファイルとして配る。この箱庭は、開発用の位置シミュレーター（F-06）の画面としても使えるので、家で開発する目的とも合う。
- 「遊べる地域を選んで入る」は、地域パックの一覧画面にする。MVP は立山・富山の1地区だけにし、生成スクリプトが他の地域にも通用するかを、2地区目で確かめる。全世界に一気に広げるための最短ルートは、MapLibre の fill-extrusion（OpenFreeMap の建物を押し出す）を三角の斜め視点で見せる 2.5D 版。作り込んだ箱庭は、手で仕上げた地域だけにする二段構えが良い。
- 見た目は 01 で有力とした「切り絵／紙芝居の 2.5D」に合わせる。建物は輪郭を押し出した単色の塊、道や川は帯状の面にし、色は共通のパレット1枚、描画は BatchedMesh・InstancedMesh でまとめる。これは Bruno Simon の作品と同じ考え方。スマホでは影やぼかしを切る軽い設定を最初から用意する。描画命令の上限は公式の数値がないので、検証スパイクで renderer.info.render.calls と fps（02 の目標は中位機種で30fps以上）を実機で測って決める。
- カメラは、斜め上から固定角度で見下ろす視点にする（OrthographicCamera か、画角の狭い遠近カメラ）。地面が奥へ丸く転がって見える頂点シェーダーも入れる。これで地平線が隠れて、遠くの描画を省ける。three.js 向けの完成品はないので、Unity の解説を参考に自作する（1〜2日の見込み）。キャラ操作は ecctrl などを参考にしてよいが、カメラの追従は自分で書く必要がある。
- 背景の立山連峰は、地理院の DEM10B（ズーム11〜12）から作った粗い地形メッシュでよい。さらに軽くするなら、標高から作った山並みのシルエットを数枚重ねる「切り絵の書き割り」にする。後者は和風の画風に合い、スマホで最も軽い。足元の地形はズーム14前後にする。利用条件の面では、実行時に地理院タイルを読み込む方式なら出典表示だけで済む。地形を事前に作って配る方式は申請が要るかもしれないので、国土地理院に確かめる。出典表示（地理院・OSM・USGS など）は、最初からクレジット画面に入れておく。
- Gaussian Splatting は、箱庭全体の下地には使わない。代わりに「現地へ行った人だけが持ち帰れる風景」というご褒美にするのが良い。たとえば、提携した場所を撮った1場面を、家の箱庭の中に飾れるようにする。そうすれば H4（現地に行く価値）の設計とつながる。技術は Spark 2.x を使い、1場面は50万〜100万スプラットに抑える。.RAD での流し読みか SOG（100万で約10MB と試算）で、必要になってから読み込む。最初の読み込み10MB の目安には入れない。
- 撮影アプリは、規約の条件で選ぶ。Scaniverse は、商用で使うには Pro（月50ドル）以上が必要で、無料の一般向け規約は個人・非商用に限る。さらに Niantic Spatial に AI 学習を含む利用権を与える条項があり、提携先の神社や寺の映像の扱いとして問題になりうる。Polycam は帰属表示があれば商用化できるが、「娯楽目的のみ」という免責がある。どちらにしても、提携先から撮影と利用の許可を書面でもらう手順を F-72（協力先）に加える。
- ユーザーが新しく出した「現地限定のお守りや御朱印のようなもの」は、04 の現行ルール「護符・御朱印に似せない」とぶつかる。似せない別の形（例: 縁の印、土地の記念品）にするか、提携先の神社と一緒に作る正式な授与品として扱うかを、企画として決め直す必要がある。
- 次の検証スパイクに入れる候補は4つ。① 立山・富山の1地区を OSM と DEM から glTF にする生成スクリプト（osm2threejs や Blosm で下地を作るか、自作するかの比較）② 中位の Android と iPhone で、箱庭を歩いて30fps が出るか ③ Spark で50万スプラットの場面を出したときの fps とメモリ ④ 地理院タイルで山並みの背景を作ること。立山周辺の OSM に建物や道がどれだけ入っているかは、Overpass Turbo で最初に確かめる（今回は接続できず未確認）。富山市と立山町の PLATEAU 3D 都市モデルも、確認できなかった。

### 調べたこと
#### 1-a) OpenStreetMap などから道路・川・建物を取り出し、three.js で様式化した 3D/2.5D を作る方法とライブラリの例（確度: 一部確認）

大きく3つの作り方がある。

(A) 事前に作って glTF で配る（オフラインで焼く）
・OSM2World: OSM から 3D モデルを作る。glTF/glb/obj などに出力でき、JVM 版と Web 版のライブラリとしても使える。公式サイトには「コードと素材はすべてオープンなライセンス」とある。
・osm2threejs（Python）: 地名か範囲を指定して、OSM から three.js のビューア、glb、OBJ などを作る。テーマは12種類あり、「Cartoon Stylized（セル調）」や「Editorial Paper（紙の色調）」も入っている。MIT ライセンス。ただし初版は 2026-08-25、最新は 0.12.1（2026-09-06）とまだ若く、保守しているのは1人だけ。PyPI に載っている性能値（8,500棟を34ms で生成、60FPS など）は自己申告で、検証していない。
・Blosm（旧 blender-osm）: Blender に OSM と地形を読み込むアドオン。無料版は建物・道路・川・森の形と、約30m 解像度の地形まで。有料版は建物のテクスチャなどが付き、GPL で配布される（OSM Wiki の要約を検索結果で確認しただけ）。
・map3d: React Three Fiber で作られ、glb 出力ができる。README では「データの正確さは保証できない」としており、デモの段階。

(B) ブラウザでその場で組み立てる
・OSM のデータを osmtogeojson（MIT、ブラウザでも動く）で GeoJSON に変える。建物は three.js の ExtrudeGeometry（輪郭を押し出す。depth と bevel を指定できる）で立体にし、BatchedMesh などでまとめて描く。
・データの取り方に注意がいる。公開されている Overpass API の目安は「1日約1万リクエスト・約1GB」。一般向けアプリの裏側として公開インスタンスに頼るのは「問題のある使い方」と明記されており、その場合は自前で立てるよう求めている。
・全世界を相手にするなら、PMTiles（1ファイルにまとめたタイルを HTTP Range で必要な分だけ読む。S3 などに置くだけで配信できる）のようなベクタータイルを自前で配るのが筋が良い。

(C) 2.5D（地図ライブラリの上に three.js を重ねる）
・MapLibre の fill-extrusion で OSM の建物を高さ付きで押し出せる。公式例では OpenFreeMap のタイルを使っている。
・MapLibre には three.js をカスタムレイヤーとして重ねる公式例がある（影付きのモデル、3D Tiles など。例の一覧を検索結果で確認）。
・作る手間は最も小さく、全世界で動く。ただし見た目の作り込みには限りがある。

参考になるが、今回の用途には合わないもの
・Streets GL（MIT、WebGL2 の OSM 3D レンダラー）: 「独立した GPU があると良い」としており、スマホ向きではない（検索結果の要約）。
・three.js の CityGenerator: シード値から街を手続き生成するだけで、OSM は読み込まない。
・Google Photorealistic 3D Tiles: 規約で、先読み・保存・キャッシュ・オフライン利用、データの抽出やなぞり書きが禁止されている。様式化した箱庭の下地としては使えない。

公式の手段

#### 4-a) 標高データから山の地形（立山連峰の背景など）を three.js で作る方法（確度: 確認済）

標高を色で記録した画像タイルを読み、平面メッシュの高さに変える、というのが基本の方法。

日本の標高データ（国土地理院の標高タイル、PNG、256×256画素）
・DEM10B: https://cyberjapandata.gsi.go.jp/xyz/dem_png/{z}/{x}/{y}.png（ズーム1〜14）
・DEM5A / 5B / 5C: dem5a_png などの URL（ズーム1〜15）
・DEM1A: dem1a_png（一覧ページの記載ではズーム1〜17）
・どの場所でどの解像度が使えるかは「標高モデルの更新情報」の地図で確かめる、とされている。
・テキスト形式のタイルは、2024年10月から更新が止まっている。
・PNG から標高への換算式（標高の分解能 u = 0.01m）
  - x = 2^16·R + 2^8·G + B
  - x < 2^23 なら h = x·u
  - x = 2^23 なら値なし（R,G,B = 128,0,0）
  - x > 2^23 なら h = (x − 2^24)·u
  - Mapbox などの Terrain-RGB とは換算式が違うので、そのまま流用はできない。

three.js で地形にする方法
(a) 自前で作る: canvas でタイルの画素を読み、上の式で標高に直し、PlaneGeometry の頂点を上下させる。もっと効率よくするなら Martini を使う。Martini は高さの格子（一辺が 2^k+1。例: 257×257）から、詳細度の違う三角形メッシュを数ミリ秒で作る。ISC ライセンス。ただし本人が「実験的・作りかけ」としている。
(b) three-geo: 緯度経度と半径から、衛星写真付きの地形メッシュを作る。Mapbox のトークンが必須（ズーム11〜17）。
(c) geo-three（MIT）: 地図タイルの世界を three.js で描くライブラリ。CPU で作るか GPU で変形させるかを選べ、詳細度を自動で切り替える（LoD）。GPU 方式は速いが、レイキャスト（クリック判定など）ができない。
(d) MapLibre の地形表示（terrain）に地理院タイルを使う: maplibre-gl-gsi-terrain という専用ライブラリがあったが、GitHub でアーカイブされている（検索結果の要約）。

海外へ広げる場合
・AWS の Terrain Tiles（全世界の地表の標高。S3 の elevation-tiles-prod）がある。元データは SRTM・GMTED2010・ETOPO1 で、どれもパブリックドメイン。ただし「SRTM data courtesy of the U.S. Geological Survey」などの帰属表示が求められている。

目安の試算（自分で計算した値）
・富山の緯度では、ズーム12のタイル1枚が一辺約7.8km（1画素あたり約30m）、ズーム14で約2km（約7.7m）。
・遠くの山並みの背景ならズーム11〜12で足り、足元の地形はズーム14以上が要る。

## 家のバーチャル体験と現地来訪の教訓

### 企画への示唆
- おうちモードを「街を3Dで再現して歩ける空間」として作ると、バーチャル大阪（月約5,000人まで減少、2023年9月には無人）やメタバース・ソウル（約55.9億ウォンでDAU 537人、終了）と同じく「人がいない・やることがない」に陥りやすい。おうちモードの中心は空間ではなく「妖怪の悩みを聞いてほどく」という毎日の用事にし、空間はそのための舞台にとどめる。
- フィールドの単位は街全体ではなく、参道・境内・宿坊・登山口など数十mほどの小さな場にする。空間が広すぎると人と出会えないという指摘があるので、密度を保つ。「世界中を選べる地域マップ」でも、物語の入っていない地域は入れる状態にせず、「噂だけ聞こえる準備中の地」として見せる。中身のない地域を量産しないため。
- リアルタイムの多人数「街サーバー」はMVPに入れない。人のいなさは非同期の仕組みで補う。たとえば、ほかのプレイヤーが奉納した絵馬や足あと、置き手紙が残る、妖怪が「さっき別の人が来て、こんな話をしていった」と語る、など。若宮氏が挙げた非同期交流とUGCの考え方をそのまま使え、three.jsの単独プレイの作りでも実装できる。
- 家と現地の役割は最初から非対称に決めて、公開する。家では物語・関係（縁）・妖怪との会話が進む。現地では同じ縁の「本物の証」が手に入る（金縁の御朱印、絵巻に色が入る、その土地でしか授からないお守り）。ドラクエウォークの金/銀トロフィー方式にならい、家で集めても完成はするが、現地で得たものだけ格が上がるようにする。Pokémon GOのように後からリモートを絞ると大きく反発されるので、家を不利にするのではなく、現地に上乗せのご褒美を足す方向で設計する。
- 物語の本編を現地に行かないと進めない作りにはしない。遠方に住む人、高齢者、障害のある人も最後まで遊べることが、Pokémon GOの騒動の教訓。現地は「本編の門」ではなく、「本編で知った妖怪に本当に会いに行く」場所にする。
- 家で物語を進めたからこそ現地に行きたくなる流れを作る。家で聞いた妖怪の悩みが「実際の地形や社殿、景色を見ないと分からない」章で終わり、現地で答え合わせができる構成にする。黒神話：悟空の「線下存档点」や「通关文牒」のように、立山博物館や現地の寺社に物理的なチェックポイント（QRや掲示）を置く。これは富山県・立山町・寺社との提携が前提になるので、対馬市の観光大使任命のように、早い段階で自治体側の当事者を作る。
- 研究では「その場にいる感覚（presence）」が来訪意向を高めるとされるので、おうちモードの臨場感は写実的な3Dではなく、音・天気・季節で出す。現地で録った環境音を流し、実際の立山の天気や季節（雪の大谷、開山期など）を家の画面に反映して、「今、現地はこうなっている」を見せる。それが「今行きたい」のきっかけになる。VR酔いが効果を下げるという結果もあるので、PCやスマホの三人称視点でゆっくり動く方式で十分。
- 研究が示しているのは「来訪意向」までで、実際に来訪するかは確かめられていない。またバーチャル観光をよく使った人ほど実際の旅行意向が下がるという結果もある（Liu & Lehto 2022）。そのため、KPIはおうちモードのDAUではなく「家で遊んだ人の現地チェックイン率」「初めて現地に来るまでの日数」にし、最初から計測できる設計にする。位置の証明（GPS＋時刻、現地のQR）をログに残す。
- 開発中の「家で現地をまねるデバッグ機能」（位置を擬似的に入れる）と、本番のおうちモードは分けておく。データモデルの段階から、出会いや報酬に「現地で得た（verified_onsite）」というフラグを持たせ、同じコンテンツでも報酬の格が変わる仕組みを入れておく。あとから付け足すと、不正対策と公平性の調整が難しくなる。
- 短期のイベント型が主流という指摘に合わせ、現地の季節行事や開山時期に合わせて期間限定の章を出し、家でも現地でも同時に盛り上がる時期を作る。あつ森を使った自治体PRは来訪効果のデータが見当たらず、話題づくりで終わった可能性が高い。だから、出す章ごとに現地での受け皿（もらえるもの、立ち寄る場所）を必ず用意する。

## 「二つの旅」初案への批評（要点）

- **blocker** F-06（開発用の位置シミュレーター）を、縮尺を縮めた『動く絵地図』で兼ねる: 縮めた絵地図の上では距離が本物と違うため、04 が決めた数値（出会いの半径30〜50m、境内から50m以上離す、歩く速さの判定、GPS のずれ）を確かめられない。02 F-06 は『地図上のどこにでもいるふりができる』開発用の道具で、テストに必要なのは本物の座標・速さ・ずれ・時刻を再現することだ。プレイヤー向けの絵地図と一緒にすると、どちらも中途半端になる。案の中でも『同じ座標・同じデータ』と『名所を近づけて描く』が両立していない。 → 分ける。①開発用シミュレーター＝本物の座標の MapLibre 地図にデバッグ用の重ね表示（瞬間移動、歩行の再生、速さ、ずれの注入、時刻の切り替え）。1〜2日で作れる。②夢の旅＝見せ方の層。データには実座標（緯度経度）を持たせ、絵地図への写し方は地域パックごとの変換（基準点を数か所決めて引き伸ばす写像）で決める。必要なら地点ごとに『絵地図上の位置』で上書きできるようにする。共通にするのはデータとロジックで、地図そのものは共通にしない。
- **blocker** MVP の作業量: 自由に歩ける斜め見下ろしの箱庭フィールド（アバターと PC 対応込み）を2027年3月までに作る: 04 §6 の段取り（11月 試作A 約10日、12月 試作B 約5日、12〜2月 章の制作と台本約4.5万字の監修、イラストレーターは12月末に決定）には、この作業の余地がない。箱庭には絵地図の美術、アバターの歩行アニメ、カメラ、歩ける範囲の判定、地図とは別の描画系、PC の操作系が要る。しかも美術を描く人が決まっていない。04 §6.2 は PC 版を『作らないもの』にしている。 → MVP の夢の旅は『1枚の絵地図（麓の白描）の名所をタップして跳ぶ』道中双六の形にする。アバターの自由移動は作らない。絵は曼荼羅の構図（04 §3.6 の掛軸の下段・中段）を使い回し、新しい美術の量を増やさない。自由に歩けるフィールドは、3月のテストで H4 の結果を見てから作るかどうかを決める（4月以降）。
- **major** 『夢の旅でも物語は最後まで』と『えにし（ここでしか話さない打ち明け話）は現地だけ』がぶつかる: 04 では、光蔵坊のえにしの打ち明け話が札④（『和漢三才図会』の爪の話）で、第一章の結びになっている（§3.5・§4.2）。ここが現地だけなら、家だけの人には物語が最後まで届かない。逆に家でも聞けるなら、えにしは『現地だけ』と言えない。案はどちらとも決めていない。 → 『中身（札の知識）』と『受け取り方（体験）』を分ける。家では札④を、古笠の便りや ましろの『また聞き』（白描の頁）として受け取れるので、物語は最後まで読める。現地では妖怪本人がその場で語り、縁がえにしになり、曼荼羅に姿が描かれる。どちらで受け取ったかで台詞と絵が変わるようにする。このルールを最初から公開しておく。
- **major** 現地での『はじめて姿を見る』驚きが、家で先に使われてしまう（H4 が薄まる）: 04 の顔見知りの段階の台詞（『なんじゃ、わしが見えるのか』）と、序の口の『最初の妖怪は富山の町で待っている』（§2.1）は、現地の初対面を山場にした作りだ。家で先に出会い・会話・悩みまで済ませると、現地は『色を回収する作業』になりやすい。00 が避けたいと書いた『収集の作業化』そのものになる。現地だけのものが『色・えにし・印・まもり』という物と状態だけなのも、景色・身体・時間の体験として弱い。 → 夢の旅で会う妖怪は『白描（線だけ）の夢の姿』にし、声は短い台本だけにする。色のついた姿と本人の声（LLM の雑談）は現地で初めて出る。現地の初対面は『夢で会ったな…本当にいたのか』という台詞に変え、夢で見たことが再会の驚きとして返ってくるようにする。現地だけの体験には、物より『本物の山の方角を見る（まなざし）』『その場の時刻と季節』を多めに置く。
- **major** 『まもり』という名前と仕組み（妖怪からの贈り物）: 音が『お守り』そのもので、『守る』という効き目をにおわせる。04 §5.2 には『護符の効き目は語らない』『護符・御朱印に似せない』とある。しかもプレイヤーの役割は、護符を配った芦峅寺の衆徒を手本にした『現代の絵解き師』だ（03 #4・#20）。そこに『現地でまもりを受け取る』を重ねると、護符の授与をまねたものに見えやすい。神社側の受け止めは確かめていない（分からない）。 → 名前を変える（例『ゆかりの品』『おみやげ』『しおり』）。効き目や加護の言葉は使わない。形はお札・袋・紐にせず、04 にある供物や絵筆の毛・墨のような、絵解き師の道具の側に寄せる。MVP では新しい仕組みとして作らず、04 の供物（§3.7）とお糸の贈り物の枠で足りるか試す。
- **major** 『旅印』を御城印・駅スタンプに近いものとする位置づけ: 御城印は御朱印にちなんだもので、御朱印と同じくらいの大きさの紙に朱印と墨書きという体裁が多い（https://ryukyushimpo.jp/photo/entry-1537343.html 、https://www.fun-japan.jp/jp/articles/14438 ※どちらも検索結果の要約で確認）。『御城印に近い』と言っても、御朱印帳を3冊持つペルソナA（02 §3）には、結局『御朱印風』に見える。04 §5.2『御朱印に似せない』とずれる。00 の『御朱印のような記録』、01 の『オリジナルの御札デザインを神社の案内板にマーカーとして置く』も 04 のルールと食い違ったまま残っている。『旅印』という名前の商標の有無は確かめていない（J-PlatPat 未確認）。 → 『朱の印＋墨書き』の組み合わせは使わない。見た目は駅スタンプ（インク1色の絵柄スタンプ）か、絵解き師の『絵札』に寄せる。もっと良いのは、新しい収集を足さずに、曼荼羅帳そのものを御朱印帳の代わりにすること（旅で一冊が埋まっていく感覚は彩色で出す）。あわせて 00 の『御朱印のような記録』と 01 の『御札マーカー』を、04 のルールに合わせて直す。
- **major** 『本物の御朱印・お守りは社寺で正式に』と参拝マナーを案内する: 善意の案内でも、ゲームが社務所へ人を送り込む導線になる。御朱印は参拝の証で、スタンプラリーではないとされている（https://serai.jp/?p=1022806 、https://crexgroup.com/ja/travel/niche/goshuin-beginners-guide/ ※検索結果の要約で確認）。前立社壇に通常の御朱印があることは観光サイトに出ている（https://tabiiro.jp/shrine-temple/goshuin/hokuriku/toyama/ ※要約で確認、公式では未確認）。ただ 04 §5.2 は『社寺名や由緒は了承前は出さない』、§3.1 は境内を『お休み』にしている。神社の了承なしに御朱印を案内すると、この二つとぶつかる。 → MVP では御朱印・お守りの案内をゲームに入れない。入れるのは雄山神社の了承を得てからで、内容は『公式の案内へのリンク』と参拝マナーだけにする。ゲーム内のご褒美・悩み・進行とは決してつなげない（『御朱印をもらうと〇〇が開く』を作らない）。デジタル御朱印や NFT 御朱印のように、社寺側が自ら出している例はある（https://www.gizmodo.jp/2022/08/digital-goshuin.html ※要約で確認）。そのため『ゲームの外の正式なもの』として線を引くこと自体は筋がよい。
- **major** H4 の確かめ方を『同じ話を夢と現で体験した差』に変える: 同じ話を2回体験すると、2回目は場所に関係なく既視感で印象が弱まる。順番の効果と場所の効果が混ざってしまう。04 §6.3 は #17 と #18 の札（長さをそろえる）を家と現地に分けて順番を入れ替える設計で、こちらのほうがきれいに比べられる。5〜8人規模では、提案の比べ方は判定に使えない。 → 04 §6.3 の設計を残す。夢の旅は『家の条件』の器として使い、比べるのは別々の話にする。あわせて『夢で先に会っていた妖怪に現地で会ったとき、うれしかったか・作業に感じたか』を聞き取りに足す（夢→現の順の価値を見る）。
- **major** 既存の GDD 04 と要件 02 との食い違い（差分として書かれていないもの）: 案は『新しい出会いは現地だけ』を変えることだけを差分として挙げているが、ほかにも直す箇所がある。①04 §3.3 縁の表では顔見知りの条件が『現地で会う』、なじみが『悩みを1つ解く／好物を渡す（現地）』。②04 §3.4『悩みの開始と解決は現地だけ（例外: くらがり）』と、案の『悩みごと（一部）』。どれが家でできるか決まっていない。③04 §2.1 ましろの『最初の妖怪は富山の町で待っている』。④04 §3.8 と §7 #1 の提案Aは『おうちモードはスマホだけ、PC は後』で、案は『PC・スマホ』。⑤02 F-50（端末内保存）・F-51（引き継ぎ Should）。家は PC、現地はスマホで遊ぶ人にはデータの引き継ぎが前提になる。⑥04 §6.2 の試作A・B の範囲に夢の旅がない。⑦02 F-72（協力先の枠）は Could なのに、現地限定の入手が協力先の QR に頼っている。⑧04 §3.2 は LLM で話せる相手をなじみ以上にしているので、家で出会えるようにすると LLM の利用と費用の前提（§3.2 の見積もり）が変わる。 → 案に『04・02 の直す箇所一覧』を付ける。少なくとも①〜⑧について、新しい値を表にする。特に PC 対応と引き継ぎは、MVP では『PC でも開けるが正式対応はしない（引き継ぎなし）』か、F-51 を Must に上げるかを PO が決める項目として 04 §7 に足す。
- **major** 家の遊びに『立ち止まる』の代わりになる動詞がない: 04 の中心にある『立ち止まった人にだけ見える』は、現実の体を止めるから意味がある。アバターを止めるのは何の手間でもないので、家では緊張も手応えもない。そのうえ麓1エリア・妖怪5体ほどの密度で自由に歩かせると、『歩くだけの移動作業』になりやすい（00 が警戒する、地域が空っぽだと失敗するという点）。 → 家の動詞は『絵解きを聞く・稽古で語る』を中心にする（04 の稽古と金の縁取りはすでに家の遊び）。夢の旅は、衆徒が遠い檀那場で立山曼荼羅を見せて語った絵解き（03 #4）を、受け取る側で体験するものにする。地図の上を移動するより、絵の中の名所に『指を置いて耳を澄ます』（数秒待つと白描の姿が浮かぶ）を、立ち止まる動作の家版にする。
- **minor** 位置偽装対策としての QR/NFC: Web NFC は iOS Safari では使えない（https://caniuse.com/webnfc ）。iPhone は URL を書いたタグなら Safari で開ける（https://developer.apple.com/videos/play/tech-talks/702 ）。ただし、それは QR と同じで、URL を写真や SNS で共有すれば済んでしまう。ブラウザの位置は DevTools で簡単に上書きできる（https://developer.chrome.com/docs/devtools/sensors ）。Web ファーストでは位置偽装は防げない、と考えたほうが正直だ。 → 交換・ランキング・競争を作らない（02 の Won't と同じ）。そうすれば偽装しても本人が損をするだけなので、MVP では偽装を許容する。QR は不正対策ではなく、協力先の価値（送客数の匿名集計、F-73）のための仕組みと位置づける。どうしても必要になったら、時間で変わるコードや一回きりのコードを後から足す。
- **minor** ポケモンGO のリモートレイドの教訓の読み方: 反発の中心は『ルールを公開していなかった』ことではない。すでにあった遊び方を後から値上げ・回数制限したことと（公式: 『Remote Raid Passes have come to dominate the experience… in a way we never intended』 https://pokemongo.com/post/remote-raid-passes-update-2023 ）、障害のある人や地方の人が締め出されたこと（https://www.pockettactics.com/pokemon-go/remote-raid-changes ）だった。2021年の『交流できる距離』の縮小が反発で戻された件も同じ形だ（https://techcrunch.com/?p=2194393 ※検索結果の要約で確認）。 → 原則を『最初に配ったものは後から取り上げない』『家でできることは小さく始めて広げる方向にだけ動かす』に言い換える。家の範囲は MVP で一番控えめにしておく。行けない人（障害・遠方・海外）が物語から締め出されないことを、原則として明記する。
- **minor** 世界の屏風地図と『地域（国）を選ぶ』: 立山は国どころか県の一部で、選ぶ単位を国にすると粒度が合わない。国境を描くと係争地の表記の問題を抱える（一般論で、具体例は調べていない）。MVP で『他は準備中』の地域を並べると、空の約束に見える。 → 選ぶ単位は『土地（地域パック）』にし、世界図は国境を描かずにピンだけにする。2地域目が決まるまでは、屏風地図は作らない（タイトル画面で十分）。
- **minor** 地域パックをクリエイターや自治体が作れるようにする（AR City Vision）: 本当の難所はデータの形式ではなく、地域ごとの監修（F-71）、宗教者や当事者の了承、安全な配置の審査（F-05）だ。外部の人が作れるようにすると、ここが一番のリスクになる。地図を作るときは OSM 由来なら出典を表示する義務があり（https://osmfoundation.org/wiki/Attribution ）、地理院タイルを加工したら出典と加工したことの記載が要る（https://www.gsi.go.jp/kikakuchousei/kikakuchousei40182.html ）。 → パックの形式に『監修の状態、了承の記録、配置の審査結果、地図の出典』を必須項目として入れる。外部の人による制作は、審査の流れを持てるまで開かない。

### 追加のアイデア
- 夢の旅を『地図の中を歩く』ではなく『絵解きを受け取る旅』と位置づける。江戸時代の衆徒は立山曼荼羅を携えて全国を廻り、遠くの人に立山を絵で体験させた（03 #4、02 §4.2）。家は『絵解きを受ける側』、現地は『実際に行く側』という対比は、歴史の裏づけのある二つの旅になり、絵解き師の役割ともつながる。絵も、曼荼羅の構図を夢の旅の絵地図として使い回せる。
- 夢から現へ『再会』でつなぐ。家では白描の姿と短い台本だけで出会い、現地で色のついた姿と本人の声（LLM）に初めて会う。妖怪は『夢で見た顔だな』と覚え書きを使って迎える。家で遊んだことが、現地の驚きを減らすのではなく増やす方向に働く。
- 旅印やまもりを新しい収集として足さず、曼荼羅帳を『旅で一冊を埋める帳面』（御朱印帳の気持ちの受け皿）にする。現地で妖怪がその場で筆を入れる演出（彩色）を、御朱印を書いてもらう感覚の代わりにする。新しい仕組みが要らず、宗教の線も越えない。
- 協力先とは、すでにある紙のスタンプラリーに乗る。立山博物館を含む『立山ミュージアム群スタンプラリー』の台紙が県から出ている（https://www.pref.toyama.jp/documents/55937/stamprallysheet.pdf 。実際に見たが、実施期間や条件の文字は読み取れなかった）。博物館で『紙のスタンプ＋ゲーム内の色』を一緒に得られるように相談すると、協力先の負担が小さい。
- 夢の旅に、現地の『今』だけを映す。立山の時刻（日の入りと逢魔が時の計算は 04 §3.9 ですでにある）と季節の台詞を出す。海外や東京から見ても『向こうは今、日が暮れた』と分かるので、行きたくなる気持ちを安く作れる（天気とは連動させない方針は 04 §2.7 のまま）。
- MVP の後の案: 『おすそわけ』。現地に行った人が、家だけの友だちに『その場の色』を1つ分けられる（あげた人は何も得しない）。行けない人を締め出さず、『誰かが現地に行った』ことの価値は残せる。02 の Won't（交換）に当たるので、MVP 後の検討にする。
- 名所を近づけて描く絵地図の手本には、吉田初三郎の鳥瞰図が合う。大胆に誇張しながら、細部は現地をよく調べて描いている（https://www.pref.kyoto.jp/shiryokan/yoshida-index.html ）。『方角と並びは本物、距離は縮める』という案の方針を、そのまま美術の指示書にできる。
- 前例の参考: ドラクエウォークの『おみやげ』は、都道府県のランドマークでご当地クエストをクリアすると入手できる（攻略サイトの情報で、公式は未確認 https://game8.jp/dqwalk/305725 ）。現地限定の物の文化はすでにあるので、本作は物より『その場でしか起きない台詞と体験』で差をつけたほうが埋もれない。
